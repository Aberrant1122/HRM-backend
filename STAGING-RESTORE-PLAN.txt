Proposed resource boundary
Create a separate Railway staging project (hrm-staging), with staging-only MySQL 9 pinned to a verified minor/image digest, backend and frontend services on the reviewed codex branches. A separate project prevents accidental production service/variable references. Do not duplicate production variables wholesale. Keep production source on main untouched. Gate staging deployments on checks; require a reviewed production decision separately.

Use a new 5 GB database volume and fresh synthetic fixtures. Set unique staging JWT secret, database credentials, frontend/backend URLs and storage credentials. Never use production DB_URL/DATABASE_URL, production AWS keys/bucket, production reset tokens or production SMTP credentials. Database and mail sink remain on private network; only UI/API test domains are public. Seed synthetic admin, employee, client and, once enum discrepancy is resolved, manager identities. Fixture emails use example.invalid. No production HR data belongs in ordinary staging.

For storage, provision a separate private S3-compatible staging bucket and staging-only least-privilege credentials restricted to that bucket. The present client uses AWS SDK/S3 helpers; verify its actual endpoint configuration before selecting a non-AWS provider. Deny public object access; exercise signed URL scopes and unauthorized upload denial with synthetic files. Do not treat the legacy public /uploads route as resolved.

Use a private Mailpit/similar SMTP sink and staging SMTP configuration support; the present transporter accepts EMAIL_SERVICE credentials, not arbitrary SMTP host configuration. Add and test explicit sink configuration before staging invitations. A future mail adapter must fail closed if staging mail settings point to external recipients/providers. No real mail is needed for staging acceptance. The invitation portal link was changed to use the configured frontend base URL instead of a production hostname.

Disable attendance/background schedules for deterministic acceptance, then test them explicitly with synthetic fixtures. Record exact commit heads, image digests, schema migration state and environment-variable NAMES (never values). Check every rendered domain and internal connection target before first service start. Avoid npm start for initial rehearsal because it automatically runs migrations; run migrations explicitly and start node server.js after reviewing results. Existing server startup may also run schema setup: inspect and constrain it before cloud staging.

Backup inventory and production restore proof
First obtain read-only evidence from the owner: current database version/digest, backup schedule, last successful backup timestamp and size, retention, encryption/access controls, and schema migration state. Record exact RPO/RTO targets as owner decisions; daily backups imply up to roughly a day of loss and are not a promised business RPO. Proposed schedules are daily+weekly+monthly, subject to approval. Railway documents daily retention 6 days, weekly 27 days, monthly 89 days; incremental backup data is charged at volume rates. Check live account UI before enabling.
Railway volume snapshots can only be restored into the same project/environment, and restoring swaps the service volume and redeploys it. Consequently, clicking Restore on the production database is NOT an isolated staging rehearsal. Do not perform that operation during this development work.
For a safe cross-environment proof, request an approved consistent logical export from a production read-only connection by an authorized operator: transaction-consistent InnoDB dump including schema, triggers, routines/events as needed, plus migration metadata. Verify required dump privileges and GTID settings for the actual version. Encrypt the export, compute SHA-256, restrict who can access it, and agree retention/deletion before exporting real HR data. Use a separate short-lived restore project/database with no mail, no public access, no production storage credentials and no external jobs. This is sensitive-data handling requiring owner review, not part of routine synthetic staging.
Import the export there; reconcile table counts and approved totals/checksums, foreign-key integrity, trigger presence and SequelizeMeta. Test application reads without sending mail or updating payroll/HR records. Record backup age, import duration, validation duration and discrepancies. Destroy the approved temporary sensitive-data copy after evidence review according to the agreed retention. A synthetic dump/restore exercises tooling but does not prove a production backup is restorable.

Migration, sign-in and rollback decision
The local MySQL 9.5 rehearsal executes all baseline migrations, inserts and logs in an existing-style user, then adds sessionVersion and the revocation trigger. Up/down/re-up runs preserve rows, but dropping/recreating sessionVersion resets counters: this can resurrect old tokens if the same signing key is reused. Therefore the supported release rollback keeps the column and trigger. Prefer roll-forward fixes that preserve middleware enforcement.
Before release, verify trigger creation privileges, compare current schema with baseline (manager enum mismatch already found locally), and take/verify the approved backup. Apply both new migrations before starting new code; stop rollout if trigger creation fails. Prevent mixed old/new auth instances serving traffic: old code does not enforce session revocation even though the trigger records changes. Configure the intended signing secret explicitly; JWT_SECRET_KEY takes precedence over JWT_SECRET. Moving away from the previous fallback or rotating the key signs all users out. Warn the owner of that sign-in impact and verify a synthetic admin can sign in before reopening traffic.
If emergency rollback requires removing the column/trigger or restoring an older snapshot, invalidate all outstanding tokens by rotating the signing secret before serving traffic. Never run the existing migrate:undo script against production: it undoes all migrations. Do not restore a production volume without an incident-specific reviewed cutover/recovery decision.
