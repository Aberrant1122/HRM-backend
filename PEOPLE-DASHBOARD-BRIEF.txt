People/dashboard preparation — 6 November 2026
Boundary: separate from the security release. No workforce membership, HR/Accounts grants, leave policy or tax rule is approved by this brief.

Confirmed data and errors
User.role is a login role; User.status is active/inactive/suspended account access state. UserInfo mixes employment categories with probation/terminated, and stores department/reportingManager as strings. Department has an active flag. LeaveRequest has userId, pending/approved/rejected, start/end calendar dates and full/half-day mode. No notice-period field, archive lifecycle, salary revision ledger or reliable staff-membership flag exists.
Employee list currently queries role=employee, not all workforce. Its Active Employees card counts only the current page; Departments is hardcoded to four/names that do not come from configuration; On Leave counts inactive accounts. Dashboard attendance counts rows of all statuses and roles, and approved leave counts requests, so numerator/scope can disagree with employee-role denominator or double-count people. These are source findings, not production-data claims.

Policy-independent bounded implementation
Add an admin-only account summary with an explicit scope: all accounts whose current login role is employee, regardless of pagination. Do not rename this to workforce/headcount or silently include manager/admin/client. Aggregate account statuses in one SQL statement so totals reconcile within a read. Report active/inactive/suspended/unknown buckets, total and scope metadata. Separately count active configured Department records. Do not infer department configuration from employee strings.
Use those exact definitions on the existing account-list cards: Employee-role accounts; Configured departments (active configurations); Active accounts (access enabled); Inactive accounts (access disabled, with suspended separately described if shown). Remove inactive-as-leave logic rather than fabricate a leave count. Keep permissions/self-service unchanged. Card failures must show unavailable/error rather than zero or stale invented numbers. Reload aggregate counts after account deactivation; totals must not depend on the table page/search.
The account-list search is currently page-local. Label that scope or implement server search/filter matching before claiming filtered organization totals. A global account summary remains explicitly unfiltered; filtered metrics need shared server predicates and tests. New summary fields contain counts/scope only, no salary, bank, identity documents or personal contact fields.

Future workforce metrics: proposed definitions for product review
Workforce total: stable employee identities satisfying an approved staff/lifecycle predicate, independent of login role. Active workforce: workforce identities whose approved employment lifecycle is active; do not substitute account status. Former: an approved end-of-employment condition. New joiners: qualifying startDate in an explicit reporting interval. Probation: an approved lifecycle condition; end date alone can be stale. Notice: unavailable until notice dates/state exist. Unavailable lifecycle metrics must not be invented or silently zeroed.
On leave on a reporting date: proposed count of distinct approved workforce identities with a request covering that explicit date, excluding pending/rejected. Show people separately from leave-day units; duplicate requests cannot inflate people counts. Reporting date must be explicit at the API boundary. Company-zone conversion of today requires the zone decision. This does not change entitlement/year/holiday/half-day charging policy.
Attendance: report distinct qualifying people and explicit status sets against the same scope/date as the denominator; absent rows are not present. Task completion is task completion, not employee performance. Active department configuration count and distinct department assignments are separate measures with different names.

Smallest decisions needed for workforce dashboard

3. Which existing employmentStatus values map to active/former/probation, and how should missing/contradictory values be flagged? Notice/archive need explicit fields/workflow rather than inference.
