Manual direct-entry onboarding — 6 November 2026
Separate codex/manual-onboarding branches stacked on People/security. Do not add this migration or workflow to the security cutover by default. Product scope: existing admin-only administrative access; no new HR/Accounts grants, probation automation, employee numbering or lifecycle mapping. Recruitment and Indeed remain last/deferred.

Implemented
One retained manual checklist per existing employee-role account, created explicitly. Existing checklists remain readable after account status/role changes. Follow-up work reopens the same checklist with a reason; this is not a rehire lifecycle. Up to 200 configurable manual items: title, explicit responsible account, optional calendar due date, pending/completed/waived state. Responsible assignment grants no access. There is no mandatory template, invented required step or automatic reminder. No template feature was needed for this manual slice; versioned template snapshots and documents/letters/signatures are not reimplemented.

Administrative actions add/edit/complete/waive/reopen items and manually complete/reopen the checklist. Completion requires at least one item and no pending items. Completion/waiver/reopening and detail edits require reasons. Every accepted command records actor ID, action, increasing checklist version, reason and before/after details in the same transaction. No event update/delete endpoint exists. History pages in batches of 100, preserves earlier entries, and resolves responsible/actor IDs without serializing confidential user profiles or command hashes.

Concurrency/retry design
All writes lock employee then checklist in the same order. expectedVersion rejects stale edits with HTTP 409; failed validation/state transitions roll back version/data/history together. A globally unique UUID command key binds normalized payload, employee and actor by SHA256. Same-key/same-command replay is checked before stale-version rejection and adds no second event; changed actor/payload returns 409. Commit precedes response. Response/read uses a repeatable-read transaction so checklist, items and history agree. Replay returns appliedVersion plus a consistent current snapshot, not a fabricated old snapshot.
The UI keeps unconfirmed commands in per-admin/per-employee tab sessionStorage and retries the same UUID across reload after network/500 uncertainty. A definitive 4xx clears the pending command and reloads current state for explicit review. No silent stale merge or automatic second command. User entry on the existing Add Employee form remains independent: existing invitation creates inactive account; checklist actions never activate, alter role/profile/employment/probation, issue invitations or mutate payroll.

Retention and migration
Additive migration 20261106000000-manual-onboarding.js creates cases/items/events, version/command uniqueness and RESTRICT references. No HR data backfill or broad sync. Existing employee roles/status/session versions are unchanged. Populated down refuses to remove history; empty down/re-up is supported. Client deletion with any linked FK history/responsibility returns 409/deactivate guidance rather than a generic 500, including former employees converted to client. Existing ordinary client deletion behavior remains when no retained linkage exists. No production migration/merge/deployment is authorized.

Known bounded limits / next choices
Manual account-linked tracking only; no recruitment dependency. One checklist per account with explicit reopen; no rehire/archive model inferred. No manager/employee self-service even when assigned. Responsible person can be an existing account of any login role; this records responsibility and grants no entitlement. Actor/assignee names resolve current names with stable IDs retained. Checklist history is application-append-only, not a tamper-proof DB security ledger. No templates, files, signatures, reminders, default probation duration or automatic lifecycle decisions. Shared supporting features require their own concrete scope. Later business employee ID, probation decision/reminder authority/lead-time, company reporting zone and capability/lifecycle mappings remain product decisions; manual tracking does not wait for them.
